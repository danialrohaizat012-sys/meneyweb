# Meney Web — Technical Audit (14 Oct 2026)

Scope: GitHub source review of `index.html`, `catalogue-admin.html`, public catalogue rules snippet, plus owner-reported UAT. No direct Firestore admin access, emulator execution or browser penetration test was performed.

## Verified
- Public site queries only `publicCatalogue` with `published == true`, limit 100; excludes `available == false`.
- Owner publisher checks authenticated `users/{uid}` with `active === true`, `role === owner` before loading products.
- Owner publisher writes an explicit sanitized subset into `publicCatalogue`; it does not write POS `products`.
- Firestore rules snippet restricts catalogue writes to owner, allows public reads of published docs.
- Error/empty-state messages exist.
- User reported successful login, publish, unpublish, and anonymous UI visibility checks. GitHub Actions static UAT passed.

## Findings

### HIGH — Published stock/price can become stale
Owner publisher copies `price` and computes initial `available` from POS stock, but POS updates do not automatically update `publicCatalogue`. A sold-out item may still show available. **Recommendation:** either (A) add a trusted backend Firestore trigger with idempotent stock/price sync and controlled public fields, or (B) explicitly label site availability as enquiry-only and implement a manual reconciliation process. Do not make POS `products` publicly readable.

### MEDIUM — No automatic pagination
Public storefront queries `limit(100)`, and admin renders first 100 matching POS items. More records may not be discoverable. Add cursor pagination, and server-side search strategy when catalogue grows.

### MEDIUM — Admin exposes existing published values by default
The publish form prioritizes previous public price and availability over current POS values. If POS stock/price changed, republishing may preserve stale values. Add a visible diff / source stock-price snapshot before publish.

### MEDIUM — Owner role and Firebase rules need negative-case tests
Anonymous, inactive, staff and customer write denials, unpublished reads, and published-only query behavior should be tested using Firebase Emulator. UI hiding alone is not an authorization test.

### MEDIUM — Rules validation could be stronger
Current rule restricts allowed keys and checks name/price/published/sourceProductId, but does not type/length-check optional fields, image URLs or timestamp. Add validation in a separate, tested rules revision. The existing rules are already deployed: do not replace blindly.

### LOW — Public storefront is static snapshot
`getDocs` only runs on page load. Changes appear after refresh. Realtime subscription is optional.

### LOW — Manual availability override
Owner can mark available even when stock is zero. This may be intended for preorder; consider distinguishing ready-stock vs preorder rather than a single boolean.

## Gate before production
1. Test negative Firestore security cases in emulator.
2. Resolve stock/price sync strategy.
3. Test real customer WhatsApp journey and catalogue after POS sale.
4. Test mobile manually (previously deferred).
5. Verify Firebase Auth domain if adding Google sign-in.
6. Set domain DNS only after staging approval.

No production data or rules changed during this audit.
